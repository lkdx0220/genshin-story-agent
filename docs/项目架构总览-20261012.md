## 一、分层架构

```
┌── 入口层 ───────────────────────────────────────────────┐
│ CLI (genshin_story_agent.py) / Flask Web API (:5000)     │
│   └ SSE 流式（tool_calls / answer / done 事件）           │
├── Agent 图（LangGraph，6 节点，MAX_AGENT_ITERATIONS=10）─┤
│ rewrite_query → assess_query → plan_agent ⇄ tool_executor │
│                → answer_agent → END                       │
│   plan_agent 内嵌【关系预取】链（见第三节，命中即跳过 LLM）│
├── 检索与证据层（app/entity_retrieval.py）────────────────┤
│ 证据分级 / 净化正文 / 来源分级 / 覆盖度契约 / presence     │
├── 工具层（app/tools/，35 个注册、34 个初始暴露）─────────┤
│ entity_query / hybrid_search / search_all / load_quest_*… │
├── 数据层（content_data/、kb_vectors/）───────────────────┤
│ 词条图 14677 条 / 向量 23513 / 提及索引 v3 / 别名映射      │
└── 规格与防漂移层（新增）─────────────────────────────────┘
   宪法 + 现状规格 + 变更提案 + cq 闸门 + CI
```

## 二、规格驱动层（新增）

| 组件 | 位置 | 作用 |
|---|---|---|
| **宪法** | `.specify/memory/constitution.md` | 不可妥协原则：P1–P7（产品不变量）+ E1–E8（工程纪律） |
| **现状规格** | `openspec/specs/<capability>/spec.md` | 系统**当前真实行为**（11 条 Requirement + 10 条**实现锚点**）|
| **变更提案** | `openspec/changes/<id>/` | Why / What / Capabilities + 需求 delta；实施后归档 |
| **归档** | `openspec/changes/archive/` | 已交付变更（001–007）与验证证据 |
| **实现锚点约定** | 各 Requirement 内 | `文件::符号`，使 `cq spec-rebuild` 能做符号级对账 |

**工作流**：先建提案 → 实施 → 端到端验证 → 归档并回写现状规格（E8）。

## 三、四条确定性关系能力（全部代码直出、零 LLM 依赖）

| 能力 | 触发 | 实现 | 线上实测 |
|---|---|---|---|
| **名单直出** | 「某任务有哪些角色出场」+ 任务名 | `plan_agent` → `_deterministic_roster_answer` → `task_cast` | **2.2s**、工具调用 0 |
| **交集直出** | 「A 和 B 一起出现过吗」 | `_deterministic_cooccur_answer` + `_extract_entity_names` → `entity_intersect` | **1.7s**、工具调用 0 |
| **presence 查询** | 「X 去过某地区吗」 | `_deterministic_presence_answer` → `presence_hits` / `format_presence` | **6.1s**、工具调用 0 |
| **覆盖度声明** | 「某分类 cast 覆盖度」 | `_deterministic_coverage_answer` → `format_coverage` | **1.5s**、工具调用 0 |

预取顺序：**名单 → 交集 → 存在性 → 覆盖度**；均位于 `plan_agent` 前置拦截区
（形状：`final_response` + 空 `messages`，`answer_agent` 的 `existing_final` 短路复用同一机制）。

## 四、防漂移层（cq v0.3.0）

```
G0 变更提案先行        人工+约定（我默认执行）
G1 提交前闸门          cq spec-gate --mode=hard        ← 本地（真门，有未提交改动时）✓
                       CI 上同名 job 自 cq 0.4.0 起用 --base 成为真门 ✓（仍保持不阻断）
G2 例行对账            cq spec-rebuild --from code --draft
                       有效信号：code_missing / covered_count（锚点即契约）
                       忽略：spec_missing（标题级反向匹配噪声）
G3 豁免成本            cq waiver --reason --ttl --change  （计入账本 kind=spec_waiver）
G4 晋升提示            cq promote（需 decisions/ 有决策记录）
```

- 配置：`.specdrift.toml`（`code_paths=app/,prompts/`；`spec_root=openspec/specs`；`change_root=openspec/changes`）
- **CI**：`.github/workflows/specdrift-gate.yml`（name: `spec-drift smoke`；仅 `app/**`、`prompts/**` 触发；
  先只报警不阻断）。**注意（已升级）**：cq **0.4.0** 起 `spec-gate --base <ref>` 比对 `<ref>...HEAD`，CI 已是**真门**；配套流程约束：**先推送变更目录、再归档**——cq 的声明匹配只认「活跃 change」（不含 `archive/`）。（历史背景：v0.3.0 时 CI 为干净 checkout，旧版只看工作区改动，
  —— 属**冒烟巡检**（校验 cq 可装、配置可读、命令可跑），**不是漂移闸门** ✗；
  真门 = 本地提交前跑 `cq spec-gate --mode=hard`。让 CI 成为真门需 cq 支持修订区间
  （`--base origin/main`，已提需求：`docs/给cq的需求单-spec-drift能力.md` 第八节）。
- 本地 CI 等价验证：干净 venv + `@v0.3.0` → 无改动 SPEC_OK；造漂移 exit 1 且精确指出路径
