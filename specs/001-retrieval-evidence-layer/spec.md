## User Scenarios & Testing *(mandatory)*

### User Story 1 - 名单与交集由代码直出，不再被模型删减 (Priority: P1)

用户问「《人前人后》里有哪些角色出场？」「胡桃和行秋一起出现过吗？」时，系统必须以**结构化数据**作答：名单/集合完整、逐项可核对、附来源与覆盖度说明，且**不出现模型自行增删**。

**Why this priority**：这是关系能力的地基。名单是结构化事实，一旦交给模型誊写就会出现删减或改写（实测把 8 人总结成 7 人，漏掉菲尔戈黛特），用户无法察觉。P1 因为它同时决定可信度与响应速度。

**Independent Test**：直接用 CLI 与线上 HTTP 各跑一次上述两题，断言：① 名单逐项齐全；② 回答带来源标记；③ 未走回答 LLM（可由耗时与日志判定）。

**Acceptance Scenarios**:

1. **Given** 知识库中《人前人后》权威 `cast` 为 8 人，**When** 用户问该任务有哪些角色出场，**Then** 回答**必须**逐项列出全部 8 人（含菲尔戈黛特），且附带来源标记与覆盖度声明。
2. **Given** 胡桃与行秋共同出场命中 7 条，**When** 用户问两人是否一起出现过，**Then** 回答列出全部命中条目，且**不得**包含"行秋仅被转述提及"的条目（如「往生堂三日无主 第二回」）。
3. **Given** 名单类工具已返回结果，**When** 生成回答，**Then** 不调用回答阶段的 LLM（用耗时与日志双重判定）。

### User Story 2 - 地区/时段存在性（presence）与"参与"分离 (Priority: P2)

用户问「瓦蕾莎在奔霄颂玉轮这次海灯节中去璃月了吗？」时，系统必须区分两件事：**是否参与该活动剧情** 与 **是否有到过该地区的证据**（彩蛋、纪念留影、摆设/物品说明、地图文本）。不得由前者推出后者的否定。

**Why this priority**：当前实现会把"不在出场人物表"当成"没到过该地区"，直接给出错误否定 —— 这类假阴性比"没查到"更危险，用户会当成事实。P2 因为它直接影响事实正确性，但依赖 P1 的交付机制。

**Independent Test**：对同一问题跑现状与目标两版，断言目标版输出包含存在性证据（或明确"无法判定"），且**任何**情况下都不出现"因为没参与活动所以没去当地"的表述。

**Acceptance Scenarios**:

1. **Given** 瓦蕾莎未进入奔霄颂玉轮出场人物表，但活动彩蛋/留影文本中出现她，**When** 用户问她在该活动期间是否到过璃月，**Then** 回答给出该存在性证据条目，并明确其证据形态（彩蛋/留影/摆设说明等），同时说明她未计入该活动出场人物表。
2. **Given** 某角色在任何条目类型中都没有地区相关证据，**When** 用户问其是否到过某地区，**Then** 回答为"当前知识库无法判定"，并附覆盖度声明。
3. **Given** 用户只问"是否参与该活动"，**When** 回答，**Then** 仅陈述参与维度，不扩展到地区判断。

---

### User Story 3 - 实体检索候选覆盖全部条目类型 (Priority: P3)

角色相关证据不只在任务条目里：活动彩蛋、摆设/物品说明、地图文本同样承载事实。检索候选必须覆盖全部条目类型，并标注证据形态与来源分级。

**Why this priority**：这是 User Story 2 的使能条件（没有候选类型放开，presence 无数据可查）；也是当前"索引只有已注册角色"缺陷的下游修复。P3 因为它是机制层扩展，价值通过 P2 体现。

**Independent Test**：对给定角色执行 presence 查询，断言返回集合包含 `[activity]` 与 `[housing]`/`[item]` 等非 task 条目，且每条带类型与来源标注。

**Acceptance Scenarios**:

1. **Given** 瓦蕾莎在 `[activity] 奔霄颂玉轮` 与两条 `[housing]` 条目中出现，**When** 执行 presence 查询，**Then** 返回这三条并标注条目类型。
2. **Given** 某条目的证据来自系列活动继承（`activity_inherited`），**When** 出现在结果里，**Then** 必须显示为非权威来源，且不得单独支撑否定结论。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：当本轮工具结果为名单类（任务→角色名单、两人交集）时，回答**必须**由代码渲染后提交，逐项完整；禁止模型增删（宪法 P5）。
- **FR-002**：确定性直出必须接在**既有**确定性直答路径上（`_get_direct_metadata_answer` 之后），不得新增平行短路分支；实现后必须用真实数据流验证（宪法 P5、E2）。
- **FR-003**：名单类判定必须做**完整性校验**（逐项核对回答是否齐全），不齐则整体替换为工具结论区块（宪法 P5）。
- **FR-004**：新增 presence 查询：输入「角色 + 地区/版本（至少其一）」，输出该角色在对应范围的存在性证据条目（宪法 P4）。
- **FR-005**：回答必须**分离陈述**"剧情参与"与"存在性"两个维度；**禁止**由"未参与某活动"推断"未出现在该地区"（宪法 P4）。
- **FR-006**：实体检索候选必须覆盖全部 `entry_type`（task/activity/housing/item/map_text 等），并标注证据形态（宪法 P4、P6）。
- **FR-007**：一切计数与证据必须取自净化正文（`story_body`），剔除任务概述/前情提要/词条元数据（宪法 P2）。
- **FR-008**：输出的来源分级必须可辨：`metadata`（权威）/ `speaker_lines`（推定）/ `activity_inherited`（非权威）（宪法 P3）。
- **FR-009**：任何否定或不确定结论必须附覆盖度声明（收录范围、其中具备权威数据的条数）（宪法 P4）。
- **FR-010**：新角色未进索引、彩蛋/留影未入库等数据缺口必须可被自动发现并归口数据管线（宪法 P7、E7）。

### Key Entities

- **任务条目（task）**：`cast`（出场人物表）、`cast_source`、`cast_scope`、`story_placeholder`、`entry_kind`、`filters`（任务类型/区域/版本）、`story_text`。
- **非任务条目（activity / housing / item / map_text）**：承载存在性证据（彩蛋、留影、摆设说明、地图文本）。
- **实体提及索引**：`entities`（含 `type`）、`mentions`（条目 + 次数）、`inverted`（条目 → 实体，用于去重）。
- **证据分级**：强（出场人物表 / 净化正文台词）、中（有动作）、弱（仅文字提及）。

## Success Criteria *(mandatory)*

- **SC-001 完整性**：名单/交集类问题抽样 ≥5 题，逐项齐全率 **100%**（0 例漏项）。
- **SC-002 确定性**：名单/交集类问题**不调用回答 LLM**；P95 响应时间 **< 15s**（基线 65s+）。
- **SC-003 无越界**：presence 类问题抽样 ≥5 题，出现"未参与活动 → 未到过该地区"式否定的例数为 **0**；证据不足时输出"无法判定"。
- **SC-004 回归**：现有 90 项测试全绿；线上冒烟（关系题 / 名单题 / presence 题 / 通用题）通过。
- **SC-005 可核对**：每项结论都能给出可复现的核对命令与输出（宪法 E3）。

## Out of Scope

- 不改数据抓取与清洗的实现（缺口按 FR-010 写成任务书交数据管线）。
- 不引入 LLM 对正文的推断作为权威数据（宪法 P6）。
- 不做跨语言（多语种）检索；不做用户自定义知识库导入。

## Assumptions

- 知识库 `cast` 中的 `metadata` 来源可信（权威），`speaker_lines` 需回退到正文分级判定。
- 条目图的 `filters` 已包含「任务类型 / 任务区域 / 版本号」，可用于 presence 的范围过滤。
- 线上服务为 Flask `:5000`，改动需重启生效（宪法环境约束）。
